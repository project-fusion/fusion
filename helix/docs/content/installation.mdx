# Installation

```sh
bun add @fusion.dev/helix
```

`@fusion.dev/helix-styles` is a required dependency, on purpose. The components
use its semantic tokens and draw nothing without them. If the elements are
installed and the tokens are missing, your page shows unstyled boxes. There is
no fallback theme.

## Import the stylesheets

```ts
import '@fusion.dev/helix-styles/helix.css'
```

This one import loads four files in the order they must load:

1. `primitives.css`
2. `tokens.css`
3. `base.css`
4. `elements.css`

The order matters, and a wrong order fails without an error. We set the order
once, inside the package, so you do not have to.

The import resolves `@fusion.dev/helix-styles` through the dependency in
`@fusion.dev/helix`, so installing `@fusion.dev/helix` is enough. Only a bundler
resolves a bare specifier like this one. If you serve CSS through a `<link>`,
link `helix.css` by its path, as [Without a bundler](./without-a-bundler)
shows.

### Import the files one at a time

Each file has its own export. If you bring your own reset or your own ramp,
import the two files you want and skip `helix.css`.

- **`primitives.css`** holds the raw ramp that the semantic layer is derived
  from. The seven `--helix-seed-*` properties are read here. Your own code
  should not name a primitive, and leaving the file out does not enforce that.
  `tokens.css` refers to a primitive 297 times, so without `primitives.css`
  every semantic token resolves to nothing. We measured a page without it:
  `--helix-color-background` computes to `rgba(0, 0, 0, 0)`, and so does every
  other color. [Theming](theming.mdx) also depends on this file, because without
  it, setting `--helix-seed-brand` changes nothing.
- **`tokens.css`** declares the semantic layer: 185 custom properties in 15
  categories, plus `color-scheme: light dark` on `:root`. The files below read
  from it, and it reads from `primitives.css`.
- **`base.css`** holds the element reset, the type scale on bare `h1` through
  `h6`, and the recipes for markup that Helix does not render. It reads tokens.
- **`elements.css`** styles elements before they upgrade. It is the file most
  often left out, because a page works without it until the page is
  server-rendered. An element that has not upgraded has no shadow root and no
  styles of its own, so the markup flashes unstyled and then jumps into place.
  `elements.css` makes that interval look like the finished page.

Import the files from a stylesheet you control, and keep them out of individual
components. The order then stays visible in one place.

## Register the elements

```ts
import '@fusion.dev/helix'
```

This import has a side effect: it calls `customElements.define` once for every
element. You can run it more than once. A second `define` for the same tag
throws an error and stops the rest of the module, so the helper behind the
import checks the registry first.

To register only some elements, import them from subpaths:

```ts
import '@fusion.dev/helix/button'
import '@fusion.dev/helix/dialog'
```

Subpaths are useful when you use a few components. Their purpose is to make
your imports explicit. The package has side effects by design, so a bundler
keeps what you import either way.

## Check the installation

Render one element and check whether it upgraded:

```ts
await customElements.whenDefined('helix-button')
console.log(document.querySelector('helix-button')?.shadowRoot !== null)
```

`true` means the definition loaded and the element built its shadow root.
`false`, or a promise that never settles, means the registration import did not
run. Usually the import is outside a `'use client'` boundary, or you imported
the subpath of a component you did not end up using.

If the element upgraded and the page still looks wrong, check the stylesheets
in the order above. The symptom tells you which layer is missing:

- No color at all means `tokens.css` is missing.
- Unstyled prose and bare headings mean `base.css` is missing.
- Components that look right once JavaScript runs, but flash unstyled before
  it, mean `elements.css` is missing.

## Framework setup

The elements are custom elements, and every framework can render them.
Frameworks differ in three ways:

- How they pass a value that is not a string.
- How they bind an event.
- Whether they need configuration to accept an unknown tag.

| | |
|---|---|
| [React](./react) | Ships a runtime bridge and `jsx.d.ts` |
| [Vue](./vue) | Ships `vue.d.ts`, needs `compilerOptions.isCustomElement` |
| [Svelte](./svelte) | Ships `svelte.d.ts`, and needs no configuration |
| [Angular](./angular) | Needs `CUSTOM_ELEMENTS_SCHEMA` |
| [Other frameworks](./other-frameworks) | Solid, Qwik, Lit, and the three rules they all follow |
| [Without a bundler](./without-a-bundler) | An import map, or the stylesheets alone |

A framework has its own page when Helix ships typings for it, or when it does
not compile Helix tags without configuration. Other frameworks work with no
setup.
