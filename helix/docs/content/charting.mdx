# Charting

The chart families are `Bar Chart`, `Line Chart`, `Area Chart`,
`Scatter Chart`, `Donut Chart`, `Heatmap`, `Sparkline`, `Trend` and the shared
`Legend`. Each has its own API page. Here is which one answers which question,
and how the data gets in, which is the same for all of them.

## Which chart

Pick by the question, not by the picture.

- **How much, compared.** `Bar Chart`. A bar's length is its value, so it always
  starts at zero.
- **How something moved over time.** `Line Chart`. It measures from the data's
  own range, so a small change still shows. Its `area` puts a light wash under
  each line, each drawn from the floor on its own and overlapping the others.
- **How a total is made up over time.** `Area Chart`. Each column is stacked on
  the one below, so the top edge is the total and a band's thickness is its
  share. This is the one to reach for when the parts add up to something, and
  `Line Chart` with `area` is not a substitute: that overlaps the series, this
  adds them.
- **Parts of one whole, at one moment.** `Donut Chart`.
- **Whether two measures relate.** `Scatter Chart`, one point per row.
- **How each day or check went.** `Heatmap`: uptime, contributions, activity.
- **The shape of a series beside its number.** `Sparkline`, with no axes. And
  `Trend` for which way one measurement moved and whether that is good news.

## The data is a table in the document

```html
<table id="revenue">
  <caption>Revenue by quarter</caption>
  <thead>
    <tr><th>Quarter</th><th>Direct</th><th>Partner</th></tr>
  </thead>
  <tbody>
    <tr><th>Q1</th><td>120</td><td>80</td></tr>
    <tr><th>Q2</th><td>150</td><td>95</td></tr>
  </tbody>
</table>

<helix-bar-chart for="revenue"></helix-bar-chart>
```

`for` points at a real `<table>` by id, and the chart reads its series from it.
That is unlike every other component in the library, and it is not a
convenience.

**A property cannot survive hydration.** A framework's server render emits
markup, and a property is not markup: an array assigned to `items` exists only
after JavaScript has run, so the server has nothing to send and the first paint
has nothing to draw. Text in the document is the one channel that both a server
and a client can see.

**And the table is not a workaround, it is the accessible version.** A chart is
a picture of numbers, and a screen reader cannot read a picture. The table is
the numbers, in the document, navigable, and the chart is the drawing of them.
Hide the table visually if it should not be seen, and the data is still there:

```html
<table
  data-hidden-visually
  id="revenue"
>…</table>
```

The caption becomes the chart's accessible name unless you set `label`, which is
usually the right words and is already written.

## Series colors

Twenty-four `--helix-color-series-*` tokens, in order. A chart with three series
uses the first three. They are ordered to stay distinguishable in that order
rather than to look good as a full set of twenty-four.

The palette wraps, and where it wraps is one number in one place, so a chart and
the legend beside it can never disagree about which color a series is.

**A chart's mark carries its own series color as a custom property**, because a
chart knows which series a bar belongs to and CSS cannot count it. That is what
lets you restyle a series from outside without knowing the drawing order.

## Legends

```html
<helix-legend for="revenue"></helix-legend>
<helix-bar-chart for="revenue"></helix-bar-chart>
```

The legend reads the same table, so the names and the colors cannot disagree
with the chart's. Pointing them at two different tables is the only way to make
them disagree, and it is not something to do by accident.

## Right-to-left

On a page with `dir="rtl"`, every axis that runs along the line starts where the
text does, on the right. The words around a drawing are HTML and turn on their
own, and the drawing turns with them, so the name under a column is that
column's name in either direction. The pointer and the tooltip read the drawing
the same way.

- **What turns.** `Bar Chart`'s columns, and its rows, which grow out of their
  names at the right. `Line Chart`, `Area Chart` and `Sparkline`, with their
  end marks. `Scatter Chart`'s horizontal axis, numbers included: one rule for
  every chart is easier to read than a numeric axis that keeps its own
  direction. `Heatmap`'s weeks, which were already a grid laid out along the
  line. A half `Donut Chart`, which is read across.
- **What does not.** Up is more in every script, so values keep their vertical
  sense, and numerals are text beside the drawing, so none reads backwards. A
  whole `Donut Chart` keeps its first slice at twelve and runs clockwise, which
  is a clock's convention rather than a script's.

A chart that should read left to right anyway, a number line in a mathematics
text for instance, takes `dir="ltr"` on the element, and the platform's own
attribute is the whole of the switch.

## Reduced motion

Charts animate on entry and on data change, and every one of them answers
`prefers-reduced-motion`. See [Motion](./motion).

## What these are not

**Not a charting library.** There is no axis configuration language, no plugin
system, and no chart type you build by composing scales. Drawings that read a
table, styled by the token system, with an accessible representation by
construction. When you need a grammar of graphics, use one.
