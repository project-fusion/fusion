# Events

Each state change sends two events. The first is a request that you can cancel.
The second is a notification that the change happened.

```ts
// The request. Cancelable, carries what is being proposed, and fires before
// anything moves. This is how you take the decision.
element.addEventListener('helix-before-change', (event) => {
  if (locked) {
    event.preventDefault()
  }
})

// The notification, under the platform's own name. Fires after the value moved,
// so it is on the target where every handler ever written expects it.
element.addEventListener('change', (event) => {
  save(event.target.value)
})
```

Most of the time you need the notification. Bind `onChange` in React or
`onchange=` in HTML and read the target, as you would for an `<input>`. Use the
prefixed event when you want to cancel the change.

Each event has its own class. The class gets the event's type to you in three
ways:

- The class name is in the manifest, so the framework typings can emit a typed
  callback. A bare `CustomEvent` would give `(detail: unknown)`.
- The package augments `HTMLElementEventMap`, which types `addEventListener`
  when you write plain HTML.
- The name is defined on the class, so a dispatch and a listener always use the
  same string.

## Why the request has a prefix and the notification does not

### Retargeting

An event dispatched inside a shadow root is retargeted so that it appears to
come from the host. A bare `input` from a `<helix-input>` would look the same
as the `input` from the control inside it. A prefixed event cannot be mistaken
for either one.

### React's event names

React's synthetic event system handles `change`, `input`, `submit`, `copy`,
`focus`, and its other event names. A prop that matches one of those names is
connected to the native event of that name. `onhelix-before-change` matches none
of them, so it reaches our event. A request needs exactly that.

### The notification uses the native name

The notification has no prefix for the same reason. `onChange` on a Helix
element goes through React's synthetic system to the native `change` event the
element sends. You use it the way you already use it on any input.

### The type map is global

`HTMLElementEventMap` is shared by every element in your application. Our event
classes extend `Event`, so an entry named `select` would still compile. It would
silently retype `textarea.addEventListener('select', …)` as carrying our detail,
which is `undefined` at runtime. We measured this. We would not see a collision
from an unprefixed name, and you would.

## Which events bubble

- **Lifecycle events** do not bubble and are not composed. These are
  `helix-before-open` and `helix-before-close`. Overlays nest, and an inner
  overlay's lifecycle must never reach the outer overlay that contains it. A
  menu that closes inside a dialog does not close the dialog.
- **Coordination events** bubble and are composed. These are
  `helix-before-select`, `helix-dismiss`, and `helix-before-change`. A parent or
  a router can intercept them across a shadow boundary, so you can use a `Tree`
  as navigation.

If you listen on a container and receive nothing, the event is probably a
lifecycle event. Add the listener to the element itself.

## Cancel a change

You can cancel the events sent before a state change. Canceling is the only way
to stop the change:

```ts
dialog.addEventListener('helix-before-close', (event) => {
  if (unsaved) {
    event.preventDefault()
  }
})
```

Every dispatched event is checked against a declaration, so every event you can
listen for is documented. A declaration needs no dispatch of its own, because a
parent declares the events its children send and a form control declares the
native event it relays.

## Names

Every Helix event follows one grammar:

- A request is named `helix-before-<verb>`. It is cancelable, carries what is
  being proposed, and is sent before anything moves.
- Its notification is the native event where the platform has one, such as
  `change` or `toggle`. Otherwise it is `helix-<verb>`, the same verb without
  `before`. It is not cancelable, carries the state now in force, and is sent
  once the change stands. A request that is refused sends no notification.
- `toggle` means open and closed, as it does on `<details>`. A checked state
  uses `helix-before-check`, followed by `change` on a form control or by
  `helix-check` elsewhere.

Two notifications use the past tense, because the plain verb is taken:
`helix-resized`, since `helix-resize` reports a measurement, and
`helix-pasted`, since `paste` is the clipboard event.

### Commands

Five events are cancelable and have no `before` in their name. Each one is a
command you can refuse, and no notification follows, because nothing is in
force afterwards to report:

- `helix-create`, a value a combobox list does not hold
- `helix-dismiss`, an element asking to be taken away
- `helix-send`, what a reader wrote in a chat composer
- `helix-shortcut`, a chord that was pressed
- `helix-terminal-link`, an address a terminal would open

### Changed in October 2026

Requests that had plain names now carry `before`, and the plain name is the
notification:

- `helix-sort`, `helix-filter`, `helix-select`, and `helix-reorder` were the
  requests on Data Table. They are `helix-before-sort`, `helix-before-filter`,
  `helix-before-select`, and `helix-before-reorder` now. The plain names are
  the notifications that were `helix-sorted`, `helix-filtered`,
  `helix-selected`, and `helix-reordered`. **A page that bound `helix-sort` to
  refuse a sort binds `helix-before-sort` now**, because `helix-sort` arrives
  after the order has moved and cannot be refused.
- `helix-navigate` is `helix-before-navigate`, and `helix-navigate` follows it
  on Pagination, Data Table, Date Picker, and Drilldown. Pagination and Data
  Table sent `helix-activate` after a page moved, and send `helix-navigate`
  now.
- `helix-select` on Carousel is `helix-before-activate`, and `helix-activate`
  still follows it.
- `helix-facet`, `helix-graph-filter`, and `helix-read` are
  `helix-before-facet`, `helix-before-graph-filter`, and `helix-before-read`,
  and each plain name is the notification after it.
- `helix-before-toggle` is `helix-before-check`, and `helix-toggle` is
  `helix-check`. A row of Table that opens sends `helix-before-expand` and
  `helix-expand`.
- `helix-reorder` on a list, a tree, or a table is no longer cancelable. Refuse
  `helix-before-reorder` to keep an item where it is.

Every stateful component also sends native events once the change is applied:

- `input` and `change` on a value control
- `toggle` on anything that opens, carrying `newState` and `oldState` as
  `<details>` does. It is a `ToggleEvent` in browsers that have one, and it is
  sent whether the change came from a reader or from assigning `open`
- `close` on a dialog
- `load` and `error` on an image

## Events in a framework

Native events use their usual props, such as `onChange`, `onInput`, and
`onToggle`, which every framework already understands. A prefixed event uses
`on` followed by the exact name, such as `onhelix-before-change`. Nothing
removes the prefix or converts it to camel case. That is React's own behavior.
See [React](./react), [Vue](./vue), and [Svelte](./svelte).
