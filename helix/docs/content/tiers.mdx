# Tiers

Helix is four packages stacked on each other. Each package has one job, and each
depends only on the packages below it.

| Package | Owns | Depends on |
| --- | --- | --- |
| `@fusion.dev/helix-styles` | Tokens and the base layer. Pure CSS | nothing |
| `@fusion.dev/helix-core` | Element base class, mixins, decorators | Lit |
| `@fusion.dev/helix-headless` | Structure, accessibility, state, form participation | `core` |
| `@fusion.dev/helix` | Presentation: tokens, parts, and the visual axes | `headless`, `styles` |

`@fusion.dev/helix-theme` and `@fusion.dev/helix-icons` ship beside the stack.
Neither is a tier, and you do not need either one to render a component.

There is no React package. We generate the framework typings into
`@fusion.dev/helix`, and the bridge that repairs React's hydration of custom
events is in `@fusion.dev/helix-core`. See [React](./react).

## Why the tiers are separate packages

**`headless` must never depend on `styles`.**

This rule lets you use the headless tier on its own. You install it and write
all of the styling yourself. Nothing about how Helix looks comes with it. If
styling moved down into the headless tier, the four packages would be one
package split across four files.

## What each tier contains

The headless tier owns what a component is and does:

- markup structure
- ARIA wiring
- slots
- events
- internal state
- form participation

It ships no CSS, no token references, and none of the visual axes.

The styled tier extends the headless tier and adds only presentation. Token
references live in the styled tier.

```ts
// headless/src/accordion/item/accordion-item.ts
// no CSS, no tokens
export class HelixHeadlessAccordionItem extends MixinControllerOpen(HelixElement) {
  protected override render() {
    return html`
      <div part="container">
        <button aria-expanded=${this.open} part="trigger" @click=${this.handleToggle}>
          <slot name="summary"></slot>
        </button>
      </div>
    `
  }
}

// web/src/accordion/root/accordion-root.ts
// extends the headless one, adds presentation only
import { styles } from './accordion-root.css.js'

@customElement('helix-accordion')
export class HelixAccordion extends HelixHeadlessAccordion {
  @property({ reflect: true })
  separation?: 'outlined' | 'plain'

  static override styles: CSSResultGroup = styles
}
```

```css
/* web/src/accordion/item/accordion-item.css */
[part='trigger'] {
  min-block-size: var(--helix-size-control);
  padding: var(--helix-space-sm);
}
```

## Style a component from your stylesheet

Elements inside the shadow DOM carry no class names for you to select. Each
structural element carries a `part`, and parts are the public API for overriding
styles:

```css
helix-accordion-item::part(trigger) {
  font-weight: 600;
}
```

To change one value, set the component's own custom property. It defaults to a
system token. Setting it restyles that one component and leaves `--helix-*` and
every other component unchanged:

```css
helix-accordion {
  --accordion-radius: 1rem;
}
```

## Hide elements until they upgrade

A custom element is an inline, unstyled box until its definition loads. Its
light-DOM children render immediately, in document order. A card first appears
as unstyled text and then changes into a card. The delay is short. It is most
visible on a server-rendered page, where the markup arrives long before the
JavaScript.

`@fusion.dev/helix` includes `elements.css`, which hides each of its tags until
the tag's definition loads:

```css
helix-card:not(:defined) {
  visibility: hidden;
}
```

**The base tier ships no such file on purpose.** There are three reasons, and
the third one affects you most.

First, hiding an element is a design choice. Below the styled tier, we ship only
the rules a component cannot work without. For example, `overflow` creates a
scrollport, and `[hidden]` is the platform's own semantics. Hiding an element
that has not upgraded is a choice between two imperfect first frames. The
content is in the markup either way, so a crawler reads it in both cases.

Second, the rule belongs to the document. A component cannot apply it from
inside, because there is no shadow root before the upgrade. The rule has to
live in your stylesheet, so the choice is yours.

Third, one file for every tag would not fit your project. You import only the
base elements you use, so a generated list would include tags you never ship.
Write the rule for the elements you have:

```css
helix-base-accordion:not(:defined),
helix-base-dialog:not(:defined) {
  visibility: hidden;
}
```

Use `visibility` so the element keeps its place in the layout and the page does
not reflow when it upgrades. `display: none` collapses the box, and the content
jumps in when the definition arrives. That replaces a flash of unstyled text
with a shift of everything below it.

You may want to hide nothing. If your first paint matters more than the final
layout, or your page has to be readable with JavaScript turned off, let the
unstyled markup show. Because of that choice, we do not write the file for you.

## Mixins and tooling

`open` and `defaultOpen` come from `MixinControllerOpen` in
`@fusion.dev/helix-core`. The manifest analyzer cannot follow a mixin into
another package. Document any API that a component gets from a mixin on the
component itself, with `@event`, `@property`, or a similar tag. Mixin API
without that documentation is missing from IDE tooltips, from the React wrapper
generator, and from the manifest that agents read.
