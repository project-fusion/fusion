# Server rendering

Every component renders on a server with no DOM. If you only use Helix
components, they work in your server components with no configuration. If you
extend a component, follow the rules below. They are the complete set.

## The server has no DOM

Lit's element shim has attributes and no element tree. `querySelector` and
`this.children` are undefined, and any code that walks the DOM throws during
rendering.

We found these two examples in Helix the first time each component got a server
spec:

```ts
// Select. `display` is read during render and reached the render root.
private get listbox() {
  return this.renderRoot?.querySelector('[part="listbox"]') ?? null
}

// Menu item. `hasSubmenu` is read during render and spread its children.
get hasSubmenu(): boolean {
  return [...(this.children ?? [])].some((child) => child.slot === 'submenu')
}
```

Before we added those two guards, neither component could render on a server.
Both worked in every browser, because a browser always has a render root and an
element tree.

**Read the element tree through `this.knownChildren`**, in `willUpdate` or in a
getter that the render calls. On a client it holds every child, and on a server
it holds none. The server renders the "not known yet" state, and the client's
first render already has the children. If you read the tree after the render,
every client renders twice, and Lit's dev build warns about that.

`this.childrenKnown` is false on a server, where the children cannot be read. A
list on a server therefore does not render its "Nothing to show" message over
items it cannot see.

## Declarative shadow DOM

If you render with Lit SSR, the declarative shadow DOM it writes hydrates in the
browser. Load Lit's hydration support before the components:

```ts
import '@lit-labs/ssr-client/lit-element-hydrate-support.js'
import '@fusion.dev/helix'
```

Hydration assumes the markup already matches the client's first render. If a
value differs, hydration does not write it, and the page keeps the server's
value. If a template differs, hydration throws. While hydrating, a component
renders exactly what the server rendered. Anything it can read only in a browser
waits for the next update:

- `this.hydrating` is true for the render that hydrates.
- `this.knownChildren` is empty during it, as on the server.
- `this.finishHydration()`, called from `firstUpdated`, requests the update
  that reads what was skipped.

The browser does two things before any script can listen. Components handle
them this way:

- **A declarative shadow root reports its slots as it is parsed.** A component
  does not rely on `slotchange` alone to find what is slotted. It reads its
  children first and uses `slotchange` for later changes.
- **The parser fetches images.** A `load` or `error` event can fire before
  hydration. A component checks the state of the image (`this.serverRendered`)
  and dispatches the event again a task later.

HTML cannot declare manual slot assignment. A component that assigns its slots
by hand therefore gets a root that can assign only by name. On such a root
(`this.assignsByName`), and only there, the component writes `slot` onto its
children with `this.route()`.

Run your page's own scripts after the definitions load. Hydration expects that
order. A property you set before hydration is one the server did not render
with.

`bun run check:spec:dsd` renders every example with Lit SSR, hydrates it in
Chromium, and compares it with the same example rendered on a client.

React server components do not use declarative shadow DOM. Their output is
replayed through DOM APIs, and declarative shadow DOM does not activate for
nodes that a script inserts. See [React](./react).

## Never initialize state in `connectedCallback`

SSR does not call `connectedCallback`. Derive state from properties, or set
initial state in `willUpdate`, which SSR calls.

## Guard generated ids

```ts
if (!this.id) {
  this.id = `helix-${crypto.randomUUID()}`
}
```

The server writes the id into the HTML. On the client, the id is already
present, so the component does not generate a new one, and both ids match.
Without the guard, the ids differ, and the association breaks on hydration.

## Put semantics on the host and presentation in the shadow root

IDREFs do not cross shadow boundaries, so `aria-labelledby` inside a shadow root
cannot resolve to a light-DOM id. Use `ElementInternals`. It writes no
attributes, so the host stays exactly as you wrote it, and hydration finds no
difference.

Labels have the same problem. `<label for>` cannot reach into a shadow root
either. For that reason:

- A field's label is rendered *inside* the control, and no wrapping element
  renders it.
- A wrapping "form field" component can own the label only by passing it down
  as a property.
- `aria-label` on a host has to be forwarded from where you wrote it.

See [Composition](./composition).

Where an id cannot reach, use an element reference. Element references resolve
outward, so an element in a shadow root can point at an element in the light
DOM. `Listbox` uses one for `aria-activedescendant`, because its options are
your elements and the element that takes focus is in its shadow root. Test for
support before you use element references. Assigning to a property that an
engine does not implement does nothing and throws no error.

## A child dispatches a ready event to its parent

A parent cannot poll for a child that has not upgraded yet. The child dispatches
a bubbling ready event, and the parent listens for it.

## Write a server spec

Every component has a `*.ssr.spec.ts` file. Breaking one rule for these specs
has produced a false pass twice:

**Never assert structure against the raw SSR string.** Declarative shadow DOM
inlines the component's stylesheet into the markup you assert against. That
stylesheet names every part, host attribute, and token the component uses.
`toContain('part="media"')` can pass because of a *selector*, and
`not.toContain('data-scrolled')` can fail because of a `:host([data-scrolled])`
*rule*. Neither result tells you what rendered.

Use these helpers:

- `withoutStyles`
- `hasPart`
- `partTag`
- `hostTag`

Match attribute bindings with a pattern, because they render across several
lines:

```ts
expect(markup).toMatch(/<a\s+part="button"/) // ✅
expect(markup).toContain('<a part="button"') // ❌ never matches
```
