# React

There is no React package. The elements are custom elements and React renders
them directly. What ships for React is a `jsx.d.ts` that types every tag and a
runtime bridge in `@helix-io/core` that repairs two React behaviors.

```ts
import '@helix-io/styled/jsx'
```

A types-only import, once, anywhere TypeScript will see it. After that
`<helix-button>` is a typed element with its real props, and a value the
component does not accept is a compile error rather than a runtime shrug.

## Bind events with `onhelix-*`

```tsx
<helix-accordion-item onhelix-before-open={(event) => track(event.detail.open)} />
```

The prop is `on` and the event name, verbatim. Not `onHelixOpen`, not `onOpen`.
React 19 forwards an unknown `on*` prop to `addEventListener` using the name as
written, so the casing is the event's own.

## The bridge

React skips everything it would have to apply imperatively while hydrating. That
is two things, and `HelixElement` repairs both.

**Event handlers** attached during hydration are stashed on the DOM node but
never bound, so an event fired before the next render finds nothing listening.
The element reads React's own stash off the node and binds what it finds, so a
handler works from the first paint rather than from the first re-render.

**Object and function properties** are dropped on both sides: React's server
renderer writes nothing for a prop whose value is an object, and the hydrate path
never applies one. An array prop therefore arrives by no route at all, and
because both halves agree, nothing warns. The element assigns them itself once it
upgrades, which is what lets a data table take its rows as a plain prop:

```tsx
<helix-data-table label="People" rows={rows}>
  <helix-table-column field="name" sortable>Name</helix-table-column>
  <helix-table-column field="team" sortable>Team</helix-table-column>
  <helix-table-column field="location">Location</helix-table-column>
</helix-data-table>
```

Only properties the component declares, and only values an attribute could not
have carried, so a string is left to the channel that already works. A `null` is
left alone too, and the component's own default stands.

The columns are elements rather than a config array for the same reason: `field`,
`sortable` and `width` are strings and booleans, so they cross to the server
intact, and `cell` and `compare` are functions on an element that can repair its
own props. Nested inside a `columns` array they would be unreachable.

**The cell values still do not server-render**, which is a separate limit and not
this one. Reading a cell needs the columns, and the columns are markup children
the server render does not hand the table, so the first paint is a labeled shell
either way. Use `helix-table` where the content has to be in the served HTML.

That is runtime code you already have, in `@helix-io/core`, and nothing to
configure. One thing to know about it: it reads a React
internal, the per-page key React stores props under. If a React release renames
that key the bridge stops repairing and your handlers go back to needing a
commit before they fire. Helix pins the React version it was measured against
and fails its own build when React moves past it, so this cannot go unnoticed.

## A declared property is a claim of ownership

This is the one thing about Helix that surprises people coming from React, and
it is a compile error rather than a surprise at runtime:

```tsx
// Does not compile.
<helix-input label="Name" value="Ada" />
```

In React, `value` on a native `<input>` without `onChange` renders a read-only
field and warns. **A Helix element is not read-only**: `value` is a seed and the
element goes on applying its own changes, so the markup below works and needs no
handler beside it.

```tsx
// Seeded: the element owns it from there.
<helix-input default-value="Ada" label="Name" />

// Mirrored: bind the notification and let the element apply.
<helix-input label="Name" onChange={(event) => setName(event.currentTarget.value)} />

// Refused: you take the decision for this one change.
<helix-input
  label="Name"
  onhelix-before-change={(event) => {
    event.preventDefault()
    setName(clean(event.detail.value))
  }}
  value={name}
/>
```

**The one habit to unlearn is refusing by not answering.** React force-restores
a native `<input>` whose state did not move and does not do this for a custom
element, so a handler that declines to call `setState` leaves the element
holding the new value. `preventDefault()` is the refusal.

*Until 26 Aug 2026 this page described the opposite, and the typings enforced
it: writing `value` was a claim of ownership, the element applied nothing until
told, and `<helix-input value="Ada" />` was a compile error without an answering
handler. The constraint is deleted along with the mode.*

See [State and control](./state-and-control) for the whole of it.

## Register in a client component

```tsx
'use client'
import '@helix-io/styled'

export const HelixElements = () => null
```

Render it once in your layout. **Your pages stay server components.** An
unregistered tag is an unknown element in the HTML that upgrades when the
definition lands, so nothing about a server component needs to change.

## There is no declarative shadow DOM

A server component's output is replayed from the flight payload through DOM APIs
rather than parsed as HTML, and declarative shadow DOM cannot activate for
script-inserted nodes. This is why `elements.css` exists: it styles the
un-upgraded markup so the interval before hydration looks like the finished page
rather than like unstyled boxes.

[Server rendering](./server-rendering) has the whole contract, and
[Using the elements](./using-the-elements) has the rest of the binding rules.
