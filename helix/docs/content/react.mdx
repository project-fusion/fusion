# React

The elements are custom elements, and React renders them directly, so there is
no React package. For React, we ship a `jsx.d.ts` file that types every tag, and
a runtime bridge in `@fusion.dev/helix-core` that repairs two React behaviors.

```ts
import '@fusion.dev/helix/jsx'
```

Add this types-only import once, anywhere TypeScript sees it. `<helix-button>`
then has typed props, and a value the component does not accept is a compile
error.

## Bind events with `onhelix-*`

```tsx
<helix-accordion-item onhelix-before-open={(event) => track(event.detail.open)} />
```

The prop is `on` followed by the exact event name. `onHelixOpen` and `onOpen` do
not work. React 19 passes an unknown `on*` prop to `addEventListener` with the
name as written, so use the event's own casing.

## The hydration bridge

While React hydrates, it skips everything it would have to apply imperatively.
That affects two things, and `HelixElement` repairs both.

### Event handlers

React stores the event handlers it sees during hydration on the DOM node, but it
does not bind them. An event fired before the next render reaches no listener.
The element reads the handlers React stored on the node and binds them, so a
handler works from the first paint.

### Object and function properties

React drops object and function properties on both sides. The server renderer
writes nothing for a prop whose value is an object, and hydration never applies
one. An array prop therefore never reaches the element, and because the server
and the client agree, React shows no warning. The element assigns these
properties itself once it upgrades, so a data table can take its rows as a plain
prop:

```tsx
<helix-data-table label="People" rows={rows}>
  <helix-table-column field="name" sortable>Name</helix-table-column>
  <helix-table-column field="team" sortable>Team</helix-table-column>
  <helix-table-column field="location">Location</helix-table-column>
</helix-data-table>
```

The element assigns only properties the component declares, and only values an
attribute cannot carry. Strings still go through attributes, which already work.
The element also leaves a `null` alone, so the component keeps its default.

The columns are elements for the same reason. `field`, `sortable`, and `width`
are strings and booleans, so they pass through server rendering intact. `cell`
and `compare` are functions, set on an element that repairs its own props.
Inside a `columns` array, the bridge could not reach them.

The cell values still do not render on the server. That is a separate limit.
Reading a cell needs the columns, and the server render does not pass the table
its markup children. The first paint shows a labeled table with no data in
either case. Use `helix-table` when the content must be in the served HTML.

### The React version

The bridge is runtime code in `@fusion.dev/helix-core`, which you already have,
and it needs no configuration. It reads a React internal: the per-page key that
React stores props under. If a React release renames that key, the bridge stops
repairing, and your handlers again need a commit before they fire. We pin the
React version we measured the bridge against, and our build fails when React
moves past it, so a rename cannot go unnoticed.

## Seed, mirror, or refuse a value

Helix differs from React in one way that surprises people. This markup
compiles, and the field stays editable:

```tsx
// Compiles, and the field stays editable.
<helix-input label="Name" value="Ada" />
```

In React, `value` on a native `<input>` without `onChange` renders a read-only
field and logs a warning. On a Helix element, `value` is a seed. The element
starts with that value and keeps applying its own changes, so the markup below
works without a handler.

```tsx
// Seeded: the element owns it from there.
<helix-input default-value="Ada" label="Name" />

// Mirrored: bind the notification and let the element apply.
<helix-input label="Name" onChange={(event) => setName(event.currentTarget.value)} />

// Refused: you take the decision for this one change.
<helix-input
  label="Name"
  onhelix-before-change={(event) => {
    event.preventDefault()
    setName(clean(event.detail.value))
  }}
  value={name}
/>
```

**To refuse a change, call `preventDefault()`.** Skipping `setState` does not
refuse it. React restores a native `<input>` whose state did not change, and it
does not do this for a custom element. A handler that does not call `setState`
leaves the element with the new value.

*Until 26 Aug 2026, this page described the opposite behavior, and the typings
enforced it. Writing `value` made you the owner of the state. The element
applied no change until you set the value, and `<helix-input value="Ada" />`
without a handler was a compile error. We removed that mode and its
constraint.*

See [State and control](./state-and-control) for the full model.

## Register in a client component

```tsx
'use client'
import '@fusion.dev/helix'

export const HelixElements = () => null
```

Render it once in your layout. **Your pages stay server components.** An
unregistered tag is an unknown element in the HTML, and it upgrades when the
definition loads. Your server components need no changes.

## Server components get no declarative shadow DOM

React inserts a server component's output by replaying the flight payload
through DOM APIs. The browser does not parse that output as HTML, and
declarative shadow DOM cannot activate for nodes inserted by script.
`elements.css` exists for this case. It styles the markup before the elements
upgrade, so the page looks finished before hydration.

[Server rendering](./server-rendering) covers server rendering in full, and
[Using the elements](./using-the-elements) covers the other binding rules.
