# Trace

Trace records every memory, context, tool call, and output as a node, with an
edge to each node it came from. Every other part of Cortex is built on this
graph, and it makes three things possible:

- `why()`, which answers where an output came from
- replay, which re-runs a trace against another model
- cascading deletion, which removes everything derived from deleted data

## What a node carries

A node's payload is typed. A replay has to rebuild the call that produced a
node, so it needs every field present and spelled the same way from one release
to the next. An untyped payload cannot guarantee that.

[//]: # (rust:fusion-cortex-trace::Detail)

```rust
use fusion_cortex_trace::{Detail, Node, NodeKind};

let node = Node::new(
    Detail::Output {
        content: "0.11.0 shipped on the 8th.".into(),
        input_tokens: 412,
        model: "local/llama-3.3-70b".into(),
        output_tokens: 9,
        prompt_version: "answer/v3".into(),
    },
    vec![],
);

// The kind is read off the detail, so it cannot contradict it.
assert_eq!(node.kind(), NodeKind::Output);
```

[//]: # (/rust)

The kind is read from the detail, so a node cannot claim to be an `Output`
while it carries a tool call's payload. The type rules that case out, and no
caller has to check for it.

| Detail | Carries | Replay |
| --- | --- | --- |
| `Source` | Raw input from outside the system | Held fixed |
| `Memory` | Fact ids, so the memory has one home in Engram | Held fixed |
| `Context` | The assembled messages, and the strategy that chose them | Recomputed |
| `ToolCall` | Tool name, arguments, and result | Recomputed |
| `Output` | Content, model, prompt version, and what it cost | Recomputed |

`ToolCall` stores its arguments and result as `serde_json::Value`. Tool
arguments can be any JSON, so a stricter type would describe a schema that
Cortex cannot enforce.

## why()

`why()` returns every node an output was derived from.

[//]: # (rust:fusion-cortex-trace::Graph::why)

```rust
use fusion_cortex_trace::{Detail, Graph, Node};

let mut graph = Graph::new();
let source = graph.insert(Node::new(
    Detail::Source { content: "when did we ship 0.11?".into(), uri: None },
    vec![],
));
let memory = graph.insert(Node::new(Detail::Memory { fact_ids: vec![] }, vec![source]));
let context = graph.insert(Node::new(ctx(), vec![memory]));
let output = graph.insert(Node::new(out(), vec![context]));

// The full derivation: which memories, which context decisions, which model.
let trace = graph.why(output);
assert_eq!(trace.len(), 4);
```

[//]: # (/rust)

`why()` follows every edge back to the start, and it stops if it finds a cycle,
which a faulty writer can create.

## Replay

Replay re-runs a trace against a different model and compares the results. It
lets you test for regressions in a system whose outputs vary from run to run:
you keep the inputs fixed and compare the outputs.

[//]: # (rust:fusion-cortex-trace::replay::Graph::replay)

```rust
// The candidate model answers differently.
let candidate = MockProvider { reply: "It shipped in September.".into() };

let replay = graph.replay(output, &candidate, &Exact).await.unwrap();

assert_eq!(replay.regressions().count(), 1);
assert_eq!(replay.scorer, "exact/1");   // the result names its judge
assert_eq!(replay.graph.len(), 3);      // a replay is itself a trace
```

[//]: # (/rust)

### What a replay recomputes

A replay recomputes the `Output` nodes in a trace and keeps everything else
fixed:

- **Inputs stay fixed.** A `Source` or a `Memory` is the question being asked,
  so re-running it would change the question.
- **Context stays fixed.** A replay measures how a different model changes the
  answer. If retrieval also ran again, you could not tell whether an answer
  changed because of the model or because of different memories. Varying
  retrieval is a separate experiment, and it needs Recall.
- **Tool calls stay fixed.** Running a tool again repeats its side effects: a
  replay of a trace that sent an email would send the email again. Running tools
  in a replay needs a sandbox and an explicit opt-in, and neither exists yet.

Replay cannot substitute a different prompt yet. Looking up the prompt that a
version names needs a prompt registry, which does not exist. A field that only
changed the version label would misreport what ran.

### The judge has to be pinned

Deciding whether two outputs give the same answer is the hard part. If a model
judges the outputs and the judge itself changes between runs, you cannot tell
which change you are measuring. So each `Scorer` reports a versioned `id()`,
every result records it, and only a judge that can be pinned to a version
should implement the trait.

`Exact` compares bytes. It is too strict for prose, but it is the only scorer
that adds no judgment of its own, so its results carry full confidence. Results
from a model judge are weaker and sit on top. Running the judge locally lets
you pin it: a hosted model can change behind the same name, which is the drift
a replay is trying to detect.

A replay is itself a trace, so `why()` and cascading deletion both work on it.
When you delete a memory, the replays that used it are deleted too.

### Order

[//]: # (rust:fusion-cortex-trace::Graph::plan)

```rust
let mut graph = Graph::new();
let source = graph.insert(Node::new(
    Detail::Source { content: "…".into(), uri: None },
    vec![],
));
// A diamond: one source, two memories, one context over both.
let left = graph.insert(Node::new(mem(), vec![source]));
let right = graph.insert(Node::new(mem(), vec![source]));
let context = graph.insert(Node::new(ctx(), vec![left, right]));

let plan = graph.plan(context);

assert_eq!(plan[0], source, "the input comes first");
assert_eq!(plan[3], context, "the target comes last");
// Both memories are recomputed before the context that reads them.
assert!(plan[1..3].contains(&left) && plan[1..3].contains(&right));
```

[//]: # (/rust)

**Use `plan()` for the order to run nodes in.** `why()` walks breadth-first
from the output, which finds every node an output depends on but does not put
them in dependency order. Reversing it works only when every node sits at one
depth, as in a chain or a plain diamond. When a node can be reached at two
depths, breadth-first order places it at the shallower one, but it has to run
before the deepest node that reads it. The result is a recomputation that reads
an input that does not exist yet, and it still looks like a valid answer.

## Cascading deletion

Deleting a memory also removes the summaries, embeddings, and outputs computed
from it. Otherwise the deleted data would live on in what was derived from it.

[//]: # (rust:fusion-cortex-trace::Graph::delete_cascade)

```rust
let removed = graph.delete_cascade(memory);

assert_eq!(removed.len(), 3);          // memory, context, and output
assert!(graph.get(output).is_none());  // derived output does not survive
assert!(graph.get(source).is_some());  // ancestors are untouched
```

[//]: # (/rust)

Trace keeps a reverse index as nodes are inserted, so a cascading deletion
needs no full scan. It then drops references to deleted parents, so the graph
stays consistent.

To honor a request to delete data, a system has to find everything derived
from that data. Provenance is what makes that possible.
